# 백로그 도출 활동 플레이북 (Backlog Generation Playbook)

프로젝트/라이브러리 라이프사이클 전반에서 백로그를 지속적으로, 균형 있게 채우기 위한 활동 방법 종합 정리.

백로그 도출 활동은 크게 두 계열로 나뉜다.

- **수렴 계열 (Convergent)** — 이미 존재하는 신호(비전, 시장, 데이터, 사용자 목소리, 코드 상태)를 관찰·수집하여 과제로 전환하는 활동. §1~5.
- **창발 계열 (Emergent)** — 의도적 교란, 역방향 사고, 우연의 제도화, 시간축 이동을 통해 아직 존재하지 않는 신호를 만들어내는 활동. §6~10.

---

## Part A. 수렴 계열 — 신호를 수집하는 활동

### 1. 탑다운 전략 및 방향성 분석

제품의 큰 그림과 장기 목표에서 구체적 태스크를 역산하는 방식.

| 활동 | 설명 |
|---|---|
| **비전 대비 갭 분석** (Vision Gap Analysis) | 이상적인 모습(To-Be)과 현재 상태(As-Is)를 비교하여, 그 차이를 메우는 기능·아키텍처·기술 스택 과제를 도출 |
| **로드맵 디컴포지션** (Roadmap Decomposition) | 분기/반기 마일스톤과 KPI/OKR 달성에 필요한 에픽(Epic)과 스토리를 하위 작업으로 분해하여 배치 |

### 2. 외부 시장 및 기술 트렌드 추적

제품 외부의 기술 변화·경쟁 환경에서 아이디어를 얻는 방식.

| 활동 | 설명 |
|---|---|
| **웹 서치 & 트렌드 리서치** | 기술 블로그, 오픈소스 생태계 변화, 업계 표준(RFC 등) 변경을 모니터링하여 선제 반영 과제 도출 |
| **벤치마킹 & 경쟁사 분석** | 유사 도메인 제품/경쟁 라이브러리의 기능 세트, API 디자인, 문서화 수준을 비교하여 Feature Parity 결핍 또는 차별화 포인트 발굴 |

### 3. 데이터 및 운영 기반 피드백 (Data-Driven)

실제 구동 환경과 사용 데이터에서 객관적 개선점을 찾는 방식.

| 활동 | 설명 |
|---|---|
| **텔레메트리 & 옵저버빌리티 분석** | 메트릭·로그·트레이스에서 성능 병목, 에러 빈도, 리소스 과소비 영역을 파악하여 최적화/리팩토링 티켓 생성 |
| **유저 분석** (Usage Analytics) | 어떤 API·기능이 많이 호출되고 무엇이 방치되는지 통계를 분석하여 UX/DX 개선 요소 반영 |

### 4. 사용자 목소리 수렴 (Voice of Customer)

실제 사용자(개발자 포함)의 목소리를 직접 수집하는 방식.

| 활동 | 설명 |
|---|---|
| **이슈 및 커뮤니티 트래킹** (Inbound Feedback) | GitHub Issues, Discord, Slack 등에서 반복 제기되는 버그·기능 제안·질문을 공식 백로그로 전환 |
| **도그푸딩 & 내부 피드백** (Dogfooding) | 개발 팀이 자신의 제품을 실제 서비스 개발에 직접 사용하며 느끼는 DX 관점의 불편(스크래치)을 발굴 |

### 5. 기술 부채 및 지속 가능성 관리 (Technical Excellence)

기능 외적으로 제품의 내부 내구성을 높이는 활동.

| 활동 | 설명 |
|---|---|
| **코드 품질 & 아키텍처 오딧** | 정적 분석 경고, 의존성 보안 취약점(CVE), 레거시 구조 개선 등 기술 부채를 정기 발굴 |
| **보안 & 컴플라이언스 점검** | 라이선스 변경 대응, 암호화 표준 준수, 인증/인가 고도화 등 엔터프라이즈 비기능 요구사항 도출 |

## Part B. 창발 계열 — 신호를 만들어내는 활동

### 6. 역발상 및 사고 실험 기반

| 활동 | 설명 |
|---|---|
| **프리모텀** (Pre-mortem) | "2년 뒤 이 제품이 망했다"고 가정하고 실패 원인을 역으로 서술한 뒤, 그 원인을 예방하는 과제를 도출. 포스트모템의 역방향 — 아직 일어나지 않은 리스크의 선제 발굴 |
| **제약 제거 실험** (Constraint Removal) | "성능 제약이 없다면?", "하위 호환을 버릴 수 있다면?" 같은 가정 하의 이상적 설계를 그리고, 현실과의 차이 중 실제로 좁힐 수 있는 부분을 추출 |
| **인버전 / 안티 백로그** (Inversion) | "사용자를 가장 짜증나게 하려면?"을 나열한 뒤, 현재 제품이 이미 하고 있는 항목을 찾아 제거 과제화 |
| **API 삭제 게임** (Subtraction Session) | 추가가 아닌 "무엇을 지울 수 있는가"만 논의하는 세션. Deprecation·단순화·표면적 축소 과제 도출. 라이브러리 관리에서 특히 유효 |

### 7. 창작·서사 기반

| 활동 | 설명 |
|---|---|
| **미래 보도자료 작성** (Working Backwards) | 아직 없는 기능의 출시 보도자료와 FAQ를 먼저 작성하고, 내러티브가 매력적이면 역산하여 필요한 작업을 백로그화 (Amazon 방식) |
| **극단 페르소나 여정 분석** | "하루 1억 건 처리", "오프라인 공장", "코드를 못 읽는 사용자" 등 극단 페르소나의 여정에서 깨지는 지점 발굴 |
| **SF 프로토타이핑** | 5~10년 뒤 도메인 시나리오를 쓰고 현재로 백캐스팅하여 지금 심어야 할 씨앗(확장 포인트, 추상화 계층) 도출 |

### 8. 우연성·탐험 기반

| 활동 | 설명 |
|---|---|
| **해커톤 / 20% 타임 / Fix-it Week** | 백로그 밖 자유 탐험을 제도화하여, 계획으로는 나오지 않는 아이템이 역유입되도록 함 |
| **랜덤 워크 코드 리딩** | 코드베이스의 무작위 파일을 팀이 함께 읽는 세션. "이게 왜 이렇게 돼 있지?"라는 반응이 리팩토링·문서화 티켓의 원천 |
| **에러 메시지 산책** (Error Message Audit) | 모든 에러 메시지를 일부러 유발시켜 나열하고, 각 메시지가 사용자를 다음 행동으로 안내하는지 평가. DX 개선 아이템 대량 발굴 |
| **크로스 도메인 차용** | 전혀 다른 분야(게임, 금융, 생물학, 도시계획)의 패턴을 이식하는 브레인스토밍. 예: 게임 온보딩 튜토리얼 구조 → 라이브러리 Getting Started |

### 9. 인공 스트레스 기반

| 활동 | 설명 |
|---|---|
| **카오스 엔지니어링 세션** | 의도적 장애 주입으로 견디지 못하는 지점을 복원력 과제로 전환. 텔레메트리가 '이미 일어난 일'을 본다면, 이것은 '일부러 일으켜서' 발굴 |
| **레드팀 연습** (Adversarial Review) | 팀 일부가 공격자·악성 사용자·경쟁사 역할로 제품을 무너뜨리는 시도를 하고, 성공한 공격 경로를 방어 과제화 |
| **신입 온보딩 관찰** (Fresh Eyes Protocol) | 신규 합류자/외부인이 문서만 보고 셋업하는 과정을 개입 없이 관찰·녹화. 막히는 모든 지점이 곧 백로그 |
| **AI 에이전트 사용성 테스트** | LLM 에이전트에게 문서만 주고 라이브러리를 사용하게 함. 에이전트가 헤매는 지점은 사람도 헤매는 지점이며, AI-friendly API/문서라는 새 품질 축 검증 |

### 10. 시간축 기반

| 활동 | 설명 |
|---|---|
| **선셋 리뷰** (Sunset Review) | 분기마다 "지금 새로 만든다면 넣지 않을 기능"을 목록화하여 제거·통합 로드맵 수립 |
| **의존성 미래 예측** (Dependency Horizon Scan) | 의존성들의 유지보수 활력(커밋 빈도, 메인테이너 수)을 점검하여 죽어가는 의존성의 교체 과제를 선제 등록 |
| **아카이브 발굴** | 과거 기각·잊힌 제안을 6~12개월 주기로 재검토. 시기상조였던 아이디어가 환경 변화로 유효해진 경우가 많음 |

## Part C. 운영 가이드

### 균형 관리

도출된 아이템이 한쪽으로 쏠리지 않도록 세 축의 균형을 태그(Label)로 관리한다.

- **비즈니스 가치** — 신규 기능, 차별화
- **기술적 건전성** — 부채, 성능, 보안
- **사용자 요청** — 버그, DX 개선

이 분류가 있어야 이후 우선순위 큐 정렬이 수월하다.

### 활동 리듬 (권장 케이던스)

| 주기 | 활동 |
|---|---|
| **상시** | 이슈/커뮤니티 트래킹, 도그푸딩, 텔레메트리 모니터링 |
| **스프린트마다** | 유저 분석 리뷰, 인바운드 피드백 정리(triage) |
| **분기마다** | 로드맵 디컴포지션, 벤치마킹, 코드 오딧, 선셋 리뷰 + **창발 세션 1~2개 로테이션** (§6~10 중 선택) |
| **반기/연간** | 비전 갭 분석, 프리모텀, SF 프로토타이핑, 아카이브 발굴 |

### 창발 세션 선택 가이드

백로그가 매너리즘에 빠졌다고 느껴질 때, 증상에 따라 세션을 고른다.

| 증상 | 처방 |
|---|---|
| 기능만 쌓이고 제거가 없다 | API 삭제 게임, 선셋 리뷰, 인버전 |
| 리스크 대비가 부족하다 | 프리모텀, 카오스 엔지니어링, 레드팀 |
| 온보딩/DX 불만이 감지된다 | 에러 메시지 산책, Fresh Eyes, AI 에이전트 테스트 |
| 장기 방향이 흐릿하다 | 미래 보도자료, SF 프로토타이핑, 제약 제거 실험 |
| 아이디어 자체가 고갈됐다 | 해커톤, 크로스 도메인 차용, 랜덤 워크 코드 리딩, 아카이브 발굴 |

### 핵심 원칙

1. **수렴과 창발의 이중 루프** — 수렴 계열(§1~5)은 상시 파이프라인으로, 창발 계열(§6~10)은 주기적 세션으로 운영한다. 수렴만 하면 점진적 개선에 갇히고, 창발만 하면 근거 없는 백로그가 된다.
2. **도출 즉시 분류** — 모든 아이템은 생성 시점에 출처 활동과 가치 축 태그를 부여한다.
3. **백로그도 부패한다** — 아카이브 발굴과 선셋 리뷰로 백로그 자체의 신진대사를 유지한다.
